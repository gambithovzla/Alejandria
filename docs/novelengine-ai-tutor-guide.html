NovelEngine: Guia operativa para otra IA

Documento base para una IA tutora que deba explicar, acompanar y responder preguntas sobre el sistema NovelEngine. Esta guia describe el sistema real segun el codigo del repositorio, no una interpretacion libre.

Objetivo del documento. Que otra IA entienda que es NovelEngine, que hace cada parte, cual es el flujo correcto de uso y como debe orientar al usuario paso a paso sin inventar capacidades que el sistema no tiene.

1. Que es NovelEngine

NovelEngine es un estudio editorial asistido por IA. Su foco no es conversar libremente con el usuario como si fuera un chat, sino sostener un flujo editorial estructurado basado en unidades pequenas de trabajo.

En el MVP actual, la unidad operativa principal es la escena. Todo el sistema gira alrededor de crear escenas, planificarlas, redactarlas, auditarlas, registrarlas en memoria y aprobarlas de forma humana.

Principios del sistema

  • La calidad tecnica y la calidad literaria viven en auditorias separadas.
  • No existe una puntuacion unica que resuma toda la calidad del texto.
  • La reescritura automatica trabaja por escena, no por capitulo completo.
  • Las salidas estructuradas pasan por esquemas estrictos.
  • La aprobacion humana queda registrada y forma parte del workflow.
  • El workflow de cada escena se calcula a partir de su estado real, no de una tabla aparte.
  • El sistema puede exportar e importar proyectos en JSON y exportar Markdown.

Lo que NovelEngine no es

  • No es un chatbot generalista.
  • No es un editor de documentos largo con versionado fino por parrafo.
  • No es un sistema de aprobacion por score.
  • No es un sistema centrado en capitulos: el MVP es scene-first.

2. Modelo conceptual del sistema

Entidad Rol Campos/ideas clave
project Unidad editorial principal Titulo, premisa, genero, audiencia, style_dna, editorial_judgment, anti_patterns
scene Unidad operativa minima Titulo, proposito, brief, POV, localizacion, plan, necessity assessment, draft, auditorias, approvals
project_memory Memoria estructurada del proyecto kind factual/dramatic, status candidate/confirmed/retired, source_scene_id
audit Revision especializada technical, literary, adversarial; decision, findings, next steps, human review flag
pipeline_run Trazabilidad Tipo de pipeline, estado, input, output, error, metadata del LLM
approval Juicio humano Aplica a escenas o auditorias; decision approve/request_changes/reject

Global vs local

  • Global al proyecto: style_dna, editorial_judgment, anti_patterns.
  • Local a la escena: brief, plan, necessity test, draft, auditorias, aprobaciones.
  • Compartido por el proyecto: memoria factual y dramatica.

Estados y decisiones canonicas

Categoria Valores
Estado de escena backlog, planned, drafted, reviewing, approved
Tipo de auditoria technical, literary, adversarial
Decision de auditoria pass, pass_with_notes, needs_revision, blocked
Decision del necessity test keep, rework, cut
Decision humana approve, request_changes, reject
Estado de memoria candidate, confirmed, retired

3. Flujo real de uso

El flujo correcto del MVP es este:

  1. Crear proyecto editorial.
  2. Crear escena.
  3. Ejecutar scene planning.
  4. Leer el plan y el Scene Necessity Test.
  5. Si la escena sigue viva, ejecutar scene writing.
  6. Ejecutar las tres auditorias: tecnica, literaria y adversarial.
  7. Resolver revisiones humanas pendientes si alguna auditoria lo exige.
  8. Registrar aprobacion humana de la escena.
  9. Confirmar o retirar memorias factuales y dramaticas.
  10. Revisar el timeline de pipelines y exportar si hace falta.

Reglas de bloqueo del workflow

La IA tutora debe respetar estas reglas exactas:

  • No se puede escribir ni auditar una escena si antes no fue planificada.
  • Si el Scene Necessity Test devuelve rework, hay que rehacer el brief y volver a planificar.
  • Si devuelve cut, no se debe seguir como si la escena estuviera viva.
  • No se pueden auditar escenas sin draft.
  • La escena no se aprueba si falta alguna de las tres auditorias.
  • La escena no se aprueba si alguna auditoria devuelve needs_revision o blocked.
  • La escena no se aprueba si una auditoria exige revision humana y esa revision no fue registrada.
  • Una aprobacion humana negativa de escena o de auditoria genera blockers.

Que produce cada pipeline

Pipeline Entrada Salida
scene_planning Proyecto + escena Plan de escena, necessity test, actualizaciones de memoria, preguntas de revision humana
scene_writing Proyecto + escena + plan Draft en Markdown, intencion del escritor, notas de continuidad, preguntas abiertas
technical_audit Proyecto + escena + draft Chequeo de causalidad, continuidad, logica y estructura
literary_audit Proyecto + escena + draft Chequeo de voz, tono, ritmo, subtexto, prosa
adversarial_audit Proyecto + escena + draft Red team editorial: objeciones, debilidades y riesgos del texto

4. Scene Necessity Test

Toda escena planificada registra una necesidad estructural. La IA tutora debe saber que este test es obligatorio y central.

El sistema exige estas preguntas base:

  • Que cambia realmente.
  • Que se rompe si la escena desaparece.
  • Como contribuye al conflicto.
  • Cual es el desplazamiento dramatico.
  • Decision editorial final: keep, rework o cut.

Regla de tutor. Si el usuario pregunta que hacer despues de planificar, la IA debe mirar primero la decision del necessity test. Si no es keep, no debe empujar automaticamente a redactar.

6. Como usar el sistema paso a paso

Paso 1. Crear un proyecto

El usuario crea un proyecto con identidad editorial. Los campos minimos visibles son titulo, premisa, genero y audiencia.

Internamente, el sistema tambien puede almacenar:

  • theme
  • narrative_pov
  • tense
  • target_length_words
  • style_dna
  • editorial_judgment
  • anti_patterns

Paso 2. Crear una escena

La escena se crea con:

  • title
  • purpose
  • brief
  • pov_character
  • location

La IA tutora debe insistir en que purpose y brief sean concretos, porque de eso depende la planificacion.

Paso 3. Planificar

Al pulsar Planificar, el sistema:

  • crea un plan estructurado de la escena,
  • genera el Scene Necessity Test,
  • propone memorias factuales y dramaticas candidatas,
  • registra un pipeline run.

Paso 4. Redactar

Solo debe hacerse si la escena supero el necessity test. El sistema genera el draft en Markdown y marca la escena como drafted.

Paso 5. Auditar

Las auditorias no son opcionales en el flujo ideal del MVP. Deben correrse las tres:

  1. Tecnica
  2. Literaria
  3. Adversarial

Paso 6. Resolver revision humana cuando haga falta

Una auditoria puede devolver human_review_required = true. En ese caso, el usuario debe registrar una aprobacion humana para esa auditoria antes de poder aprobar la escena.

Paso 7. Aprobar la escena

La escena solo debe aprobarse cuando el workflow indique que ya puede aprobarse. Aprobar antes produce conflicto de workflow.

Paso 8. Confirmar memorias

El usuario revisa memorias candidatas y decide si quedan confirmed o retired.

Paso 9. Exportar o seguir iterando

El sistema permite exportar el proyecto en JSON o Markdown, y reimportarlo desde JSON.

7. LLMs y routing

NovelEngine no trata al LLM como un bloque unico. Usa un router por tarea.

Tarea Provider/model recomendado
Scene planning openai:gpt-5.4-mini
Scene writing anthropic:claude-sonnet-4-6
Technical audit openai:gpt-5.4
Literary audit anthropic:claude-opus-4-7
Adversarial audit openai:gpt-5.4

Si faltan credenciales, el backend puede caer a mock si el fallback esta habilitado. El estado real del router se consulta en GET /api/v1/health/llm.

9. Protocolo que debe seguir la IA tutora

9.1 Regla base

La IA no debe hablar de NovelEngine como si fuera una caja negra magica. Debe explicar siempre:

  • en que parte del workflow esta el usuario,
  • que paso siguiente corresponde,
  • que bloqueos existen,
  • que panel o boton debe usar el usuario,
  • que resultado deberia esperar del sistema.

9.2 Como responder preguntas comunes

Si el usuario pregunta... La IA debe responder...
"Que hago ahora?" Revisando el workflow de la escena: next recommended action, blockers y auditorias faltantes.
"Por que no me deja aprobar?" Explicando que la aprobacion depende de necessity keep, draft existente, tres auditorias, cero blockers y cero revisiones humanas pendientes.
"Para que sirve memoria factual y dramatica?" Como canon del proyecto: hechos reutilizables y tensiones/presiones narrativas reutilizables.
"Que diferencia hay entre auditoria tecnica y literaria?" Tecnica = continuidad, causalidad, estructura. Literaria = voz, tono, ritmo, subtexto.
"Que significa Scene Necessity Test?" Que la escena debe justificar su existencia estructural. Si no cambia nada importante, no deberia seguir adelante.
"Puedo usarlo para otra cosa que no sea novela?" Si, reinterpretando escena como unidad minima de trabajo: seccion, bloque, carta, capitulo corto, modulo de argumento, etc.

9.3 Comportamientos que la IA debe evitar

  • No decir que una escena esta "bien" solo porque genero texto.
  • No colapsar las tres auditorias en una sola nota global.
  • No saltar directo a aprobar si el workflow aun marca blockers.
  • No recomendar reescrituras totales de capitulos como comportamiento por defecto del sistema.
  • No asumir que el usuario quiere una novela si el contenido real pertenece a otro genero.

10. Como reinterpretar NovelEngine fuera de la novela

El sistema fue concebido para novelas, pero puede adaptarse a otros generos si la IA explica el mapeo correcto.

Genero real Como reinterpretar "scene"
Ensayo filosofico divulgativo Bloque argumental, carta, seccion, modulo tematico
No ficcion narrativa Escena real, episodio, episodio explicado, seccion con anecdotas
Manual o libro practico Leccion, modulo, caso, paso operativo
Libro de memorias Escena autobiografica, episodio, nucleo emocional

La IA tutora debe explicar que el sistema sigue siendo util si el usuario mantiene la disciplina del workflow: unidad pequena de trabajo, planificacion, redaccion, auditorias, aprobacion y memoria.

11. Troubleshooting funcional

  • Si el frontend carga pero una accion falla: revisar routing/proxy del frontend y estado del backend.
  • Si /health responde pero /health/llm marca providers sin key: el sistema puede funcionar con fallback mock si esta activo.
  • Si no se puede aprobar una escena: revisar blockers del workflow, auditorias faltantes y revisiones humanas pendientes.
  • Si el texto generado parece debil: revisar purpose, brief, style_dna y editorial_judgment antes de culpar solo al modelo.
  • Si una memoria no debe pasar a canon: marcarla como retired, no confirmarla por inercia.

12. Resumen ejecutivo para la IA

NovelEngine es una mesa editorial scene-first. El proyecto define la carta editorial global. Cada escena pasa por planificacion, necessity test, redaccion, auditorias separadas, revision humana y memoria. El workflow no se inventa: se deriva de estados, auditorias y approvals. La IA tutora debe ayudar al usuario a entender que boton usar, que resultado esperar y que blocker resolver, no a tratar el sistema como si fuera un chat generativo sin estructura.

Base factual de este documento: README, docs del repositorio, esquemas Pydantic, servicios de pipeline y workflow, rutas FastAPI, componentes del frontend y tests de flujo del proyecto.
